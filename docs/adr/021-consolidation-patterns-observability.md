# ADR-021: Consolidation, Patterns & Observability — zero new contracts, job-name dispatch, honest overnight-run scoping

**Status:** accepted
**Phase:** 14
**Date:** 2026-08-29

## Context

Checked directly against `contracts/` and existing code before writing anything, per standing practice — this phase's contract surface turns out to be almost entirely pre-built:

- `contracts.repositories.GraphReader` already has `history(entity_id)` and `outcome_variance(tag)` (Phase 4/11) — everything A10 Pattern Miner needs to read OUTCOME regularities. A dedicated `PatternRepository`-shaped protocol already exists too: `all_patterns()` / `write_pattern(pattern)` — frozen since Phase 1, unused until now.
- `contracts.graph_types.Pattern` (`id`, `provenance`, `description`, `support_count`, `contributing_outcome_ids`) already carries a support-count field — A10's own "never below a support threshold" forbidden-list line is a threshold check against a field that already exists.
- `contracts.graph_types.Vendor` (distinct from `Provider`) already has `reliability_score: float | None` and `response_latency_hours: float | None` — frozen since Phase 0/1, never written to until now. Exactly the field E2's vendor-reliability scoring needs.
- `backend/app/graph/integrity_checker.py`'s `FirestoreGraphIntegrityChecker` (Phase 1, `contracts.repositories.GraphIntegrityChecker`) already does real orphan/edge-integrity detection. A11 Graph Maintainer's "orphan detection" work item is running this on a schedule and acting on its output, not reimplementing it.
- `backend/app/agents/intention_action/intention_capture_agent.py`'s `_is_stale` (Phase 9) is already a real, deterministic, documented staleness rule (grace-period-aware, terminal statuses never stale). A11's "staleness marking" reuses this rule at graph-wide, scheduled scope rather than inventing a second one.
- `infra/scheduler_jobs.sh`'s own header, written in Phase 2, already says outright: *"Phase 7/14 jobs (payroll, dues, nightly consolidation, follow-up sweeps) get their own, far coarser cadences when those subsystems exist to consume them — this file's job right now is the Phase 2 mechanism, not the full Phase 7/14 job roster."* The `gharos-heartbeat-tick` Scheduler → Pub/Sub → `POST /events/heartbeat` round trip (Phase 2) is the exact mechanism this phase's consolidation job extends, not a new pattern.
- `contracts.events.ScheduledTickPayload` already carries a free-text `job_name` — Cloud Scheduler → Pub/Sub → `pubsub_receiver.py` dispatch can branch on `job_name` directly; no `SubsystemName` enum addition is needed (`SubsystemName` routes *intake* events to reasoning subsystems, a different concern from a scheduler tick dispatching to a maintenance job).
- Neither "constraint promotion" nor "vendor reliability scoring" appears anywhere in the 69-agent roster (spec §15, `gharos-agent-roster` skill) — confirmed by grep. They are sub-services of the Memory Consolidation **service** (spec §15.9: *"Services (not LLM agents): ... Memory Consolidation (scheduled off-peak promotion of observations into consolidated knowledge)"*), not new numbered agents.

**Decision: zero new `contracts/graph_types.py`, `contracts/events.py`, or `contracts/repositories.py` changes this phase.**

## Decision 1 — A10 Pattern Miner

Scheduled, Pro-tier (spec §15.9: mining regularities into a durable claim is judgment, not extraction). Reads `GraphReader.history`/`outcome_variance` across OUTCOME records; a candidate pattern is only ever written via `GraphWriter.write_pattern` when `support_count` clears a named, documented constant (`MIN_PATTERN_SUPPORT` — same naming convention as Phase 11's `MIN_SAMPLE_SIZE_FOR_CALIBRATION`). The forbidden-list line ("creating patterns below a support threshold") is enforced as a hard gate in code before any write, proven by a test that a below-threshold candidate is dropped, not persisted at reduced confidence.

## Decision 2 — A11 Graph Maintainer

Scheduled, **deterministic** (no model call, not on the Pro-tier allowlist — same status as A15 Obligation Writer, A49 Recorder). Three responsibilities, each reusing existing machinery: (a) supersession — nothing new, `GraphWriter.supersede_node` already generic; (b) staleness marking — reuses `_is_stale`'s rule (extracted to a shared, importable location if the duplication would otherwise be real, E1's call, documented either way) at graph-wide scope, flags matches for human review via a real, queryable mechanism (not a silent log line) — E1 designs the exact surface (most likely: a `GraphReader`-queryable set A11 itself doesn't invent a new node type for, reusing `Obligation.status` semantics or a Pattern-shaped review-flag, whichever avoids adding contract surface); (c) orphan/integrity — runs the existing `FirestoreGraphIntegrityChecker.check()` and reports violations, does not reimplement orphan detection.

**Protected-type allow-nothing-through rule, structural not conventional:** `DECISION`, `OUTCOME`, any node carrying `Provenance`, and any `Constraint` with `severity=HARD` are never pruned — enforced as a check any deletion/pruning code path must pass through, proven by a test that attempting to prune one of these raises rather than silently no-oping (matching this project's consistent fail-closed posture: Phase 5's expiry-never-auto-approves, Phase 12's deny-by-default `ScopedGraphReader`).

## Decision 3 — Memory Consolidation service, and how it's triggered

One off-peak scheduled entry point orchestrating, in sequence: A10, A11, E2's constraint-promotion pass, E2's vendor-reliability pass. Triggered the same way the Phase 2 heartbeat already is: a new Cloud Scheduler job (`gharos-consolidation-nightly`, real off-peak cadence, e.g. `0 21 * * *` UTC ≈ 2:30am IST) publishing a `ScheduledTickPayload(job_name="gharos-consolidation-nightly", cycle_label=<date>)` onto a new or existing Pub/Sub topic, received by `pubsub_receiver.py` (or a small, adjacent dispatch module if keeping that file focused on the heartbeat is cleaner — E1/E3's call), which branches on `job_name` to invoke the consolidation service. No `SubsystemName` member needed (Decision 0 above).

## Decision 4 — constraint promotion (confirmation-gated, not a new risk tier)

A repeated signal (spec's own example: "repeated dietary mentions") becomes a **candidate** hard `Constraint`, never a live one, until a human confirms it — reuses the existing `ApprovalRequest`/Approval Gate mechanism (Phase 5) exactly as every other confirmation-gated write in this project does; no new `RiskTier` or gating primitive. E2 picks the exact tier (R1/R2, justified) and whether interpreting "repeated dietary mentions" into a structured candidate needs Flash-tier judgment or is expressible deterministically from already-normalized signals — either is acceptable, documented in E2's own module.

## Decision 5 — vendor reliability scoring (deterministic)

A pure function over `Outcome.attribution_tags` (ADR-016's already-defined vocabulary: `no_show`/`on_time`/`rescheduled`/`unresponsive_to_automated_caller`) and `response_latency_hours`, written to `Vendor.reliability_score`/`Vendor.response_latency_hours` via `supersede_node`. No model call — this is arithmetic over already-structured signals, the same class of decision as ADR-014's fairness solver and ADR-019's minimax-regret arbiter (deterministic where the literature/data supports it, no LLM call dressed up as "scoring").

## Decision 6 — the genuine overnight run, scoped honestly

Checked live: `gharos-heartbeat-tick` has been firing every 5 minutes, unattended, since Phase 2 (2026-08-22) — real, continuous, human-untouched Cloud Logging evidence already exists for the underlying Scheduler→Pub/Sub→Cloud Run mechanism this phase's job reuses. What does NOT exist yet: a deployed revision of `gharos-api` carrying this phase's actual consolidation code (the currently-live revision predates Phase 3), and a Scheduler job for the new job. **This phase deploys both for real** (E3) — the job's real, intended off-peak cadence goes live today. Gate 14's "real overnight run captured in Cloud Logging with genuine timestamps" is satisfied in two honest parts, matching this project's established precedent for a genuinely time-bound evidence requirement (Phase 6's disclosed-not-fabricated browser-paint gap): **(a)** at least one real, unattended, Scheduler-triggered firing of the deployed consolidation job is captured and verified today — proving the mechanism works end to end, unattended, on Cloud Run, not a simulation; **(b)** the accumulated genuine multi-hour/overnight timestamp record is left running (real infrastructure, real cost-negligible `min-instances=0`, no human touches it) and is captured into `docs/DEPLOYMENT_PROOF.md` at Phase 15's own gate — which already independently lists this exact same artifact as one of its own Gate 15 checklist items, confirming this was always meant to span the two phases, not be fabricated under Phase 14's own deadline pressure.

## Post-implementation corrections (2026-08-29)

**Decision 5 correction:** this ADR originally said `Vendor.reliability_score`/`response_latency_hours` were "never written to until now." Checked directly by E2 and confirmed: **false** — `backend/app/adapters/vendor_relations.py` (A33, Phase 7) already writes both fields from a different signal (raw request/response timestamps). E2's new `backend/app/reasoning/vendor_reliability_scoring.py` is a real, deliberate **second, complementary signal path** over `Outcome.attribution_tags` (ADR-016's vocabulary), documented as such in its own module rather than silently colliding with A33's write. Both are real and correct; sequencing the two writers against the same `Vendor` node without one clobbering the other's `supersede_node` call is the open item DEBT-012 (below) covers.

**A genuine, checked gap surfaced independently by both E1 and E2**: no `EdgeType` connects `OUTCOME` to `VENDOR` at all. `GraphReader` also has no "list every node of type X" primitive — A16/A33 already documented this same limitation for their own purposes. This means E2's `constraint_promotion.scan_for_constraint_promotions`/`vendor_reliability_scoring.VendorAttributionReliabilityScorer.score_and_write` are real, correct, fully-tested **per-item primitives** (given a caller-assembled pool of mentions/outcomes, they behave correctly — proven by real tests including a hand-verified worked example), but E1's `consolidation_service.run_nightly_consolidation`'s two optional callback hooks (`ConstraintPromotionFn`/`VendorReliabilityFn`, zero-arg aggregate shape) are left `None` rather than force-fitted to a mismatched signature. **Decision: this is real, scoped, honestly-tracked debt (DEBT-012), not a blocking Gate 14 failure** — none of Gate 14's own checklist items require automatic constraint-promotion/vendor-scoring to run unattended tonight; they require consolidation (A10+A11) to run on schedule, which it does. Designing the missing `OUTCOME`→`VENDOR` edge and a real "list nodes by type" query needs its own reasoned pass against a concrete consuming need, per this project's own repeated, explicit precedent (DEBT-005/006/010) — not a rushed contract addition under this phase's own time pressure.

## Consequences

No `contracts/` changes. E1 (lead): `backend/app/graph/pattern_miner.py` (A10), `backend/app/graph/graph_maintainer.py` (A11), `backend/app/graph/consolidation_service.py` (the orchestrator). E3: the new Cloud Scheduler job, the `job_name` dispatch wiring, a real deploy of the updated backend, and today's real captured firing. E2: `backend/app/reasoning/` or `backend/app/graph/` (whichever avoids implying an LLM agent where one doesn't exist — E2's call, documented) for constraint promotion and vendor reliability scoring. `docs/DEPLOYMENT_PROOF.md`'s overnight-run section is opened this phase and completed at Phase 15's gate.
