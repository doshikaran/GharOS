# ADR-019: Household Council — scoped subgraph reader as a real registration-level mechanism, minimax-regret arbiter, one new `ConstraintKind`

**Status:** accepted
**Phase:** 12
**Date:** 2026-08-28

## Context

Spec §12.2, read in full before writing anything here per PHASES.md's own instruction: the Council's legitimacy rests on agents differing in **information and interest**, never opinion — "no two agents may have identical tool access and identical objectives," positions are reported and never averaged by an LLM, resolution is computed by deterministic code, and the Council never makes the final call on an R4-tier decision.

`contracts/repositories.py`'s `GraphReader` Protocol has carried this line since Phase 1: "Council specialists (A42-A46) each get a GraphReader restricted to their own domain subgraph (spec §12.2 — mutually distinct T0 scopes is a registration-level constraint, tested, not a convention)." Checked directly: **no such restriction mechanism exists anywhere in this codebase.** Every current `GraphReader` consumer (A28 Reconciliation, all of Phase 11's Simulator agents) holds a raw, unscoped reader. This is not a gap discovered as debt — it is this exact phase's own job, named as such since Phase 0.

`Decision`/`Branch`/`CouncilPosition` are frozen, unused-until-now node types (confirmed again this phase, same as Phase 11). `GraphReader.concession_ledger`/`decisions_touching`/`FirestoreDecisionRepository.branches_for`/`positions_for` already exist and are generic to any `Decision`, not chore-allocator-specific — Phase 8's renegotiation flow already proves the `CONCEDED_BY` write/read round-trip for a non-Council `Decision`. `ValuationProfile` (`person_id`, `costs: dict[str, float]`, sparse by omission, `elicitation_method`) is Phase 8's cardinal-cost-matrix shape — checked directly, nothing about its shape is chore-specific; only its *values* are.

## Decision 1 — `ScopedGraphReader`: a real, registration-level restriction, not a convention

New `backend/app/graph/scoped_reader.py` (E1). `ScopedGraphReader` wraps a real `GraphReader` and a frozen `GraphSubgraphScope` (a predicate over `object`, since this codebase's 18 node types are plain dataclasses distinguished by `isinstance`, not a `NodeType` string enum — there is nothing to switch over except the type and its own fields). Every `GraphReader` Protocol method that can return domain-relevant objects (`get_node`, `neighbours`, `blast_radius`, `blast_radius_multi`, `history`, `outcome_variance`, `effort_evidence`) filters its result through the scope predicate. Every household-wide/audit-oriented method a domain specialist has no real business calling (`unexplained`, `unverified`, `expected_but_absent`, `spend_by_category`, `decisions_touching`, `concession_ledger`, `series`, `load`, `path`, `conflicts`) raises `OutOfScopeGraphAccess` unconditionally — **deny-by-default, allow-list explicit**, the same fail-closed posture this project has used consistently (Phase 5's expiry-never-auto-approves, Phase 10's conservative disclosability heuristic).

Five frozen scope constants, one per specialist, checked against spec §12.4/§12.5's own worked-example language for which subgraph each one actually reads:

| Specialist | Scope predicate | Spec basis |
|---|---|---|
| A42 Finance | `LedgerEvent`, `RecurringCommitment` | "queries the Ledger subgraph" |
| A43 Care | `Constraint` where `kind in {MEDICAL, MOBILITY}`; `Person` (capability flags only: `has_medical_proxy`, mobility-relevant fields) | "queries the constraint/medical subgraph" |
| A44 Education | `Constraint` where `kind == EDUCATION` (new this phase, see Decision 2) | "queries the education subgraph: exam years, admission cycles, transfer windows, catchment" |
| A45 Logistics | `Obligation` (unfiltered); `Constraint` where `kind == SCHEDULE` | "queries the obligation subgraph: real recurring trips, distances, capacity requirements" |
| A46 Legal | `Constraint` where `kind in {LEGAL, CUSTODY}`; `SourceDocument` | "documentation, society rules, regulatory requirements" |

These five sets are **fully disjoint** — stronger than spec's own minimum bar ("no two agents share both tool access *and* objective," which permits partial overlap as long as objectives differ). Full disjointness was reachable here without contortion and makes Gate 12's "if two specialists were swapped, would output change?" question trivially, structurally true rather than an empirical hope. `test_scoped_graph_reader.py` proves disjointness by construction (pairwise intersection check across all five) and proves each specialist's own constructor accepts nothing but its own `ScopedGraphReader` — no specialist module may import an unscoped `GraphReader` type at all, checked by the same AST-based boundary-test pattern already twice-used this project (`test_action_construction_boundary.py`, Phase 7/10's arbitration-import checks).

## Decision 2 — `ConstraintKind.EDUCATION`

Checked all 8 existing kinds first: none covers exam years, admission cycles, transfer windows, or catchment. `SCHEDULE` is a fixed weekly time block (ADR-015's own formal `structured` key schema: `days_of_week`/`start_time`/`end_time`) — a board-exam year is not that shape at all, it is a validity-window fact (`Constraint.validity_start`/`validity_end` already exist and fit perfectly). A 9th, minimal, additive `ConstraintKind` member is the honest fix, the same class of decision as ADR-013 (a genuinely new shape, added only once a real consumer needed it) — not a workaround for A44's `ScopedGraphReader` scope; A44's scope is a *consequence* of this type existing, not the reason for adding it.

## Decision 3 — the mechanism arbiter: minimax regret with leximin refinement, not Nash welfare or a utilitarian sum

Spec §12.3 Phase 6: "a deterministic arbiter computes the outcome from the published interest scores and constraints — the same fair-division machinery as the Allocator, applied to a decision rather than chores." Read literally this cannot mean reusing ADR-014's round-robin picking sequence unchanged — round-robin *partitions many items among people*; the Council *selects one shared option from a small discrete set*, a different problem shape entirely. "Same machinery" is read here as *the same discipline*: pick a literature-real, defensible mechanism suited to *this* problem's actual shape, exactly as ADR-014 did for chores.

**The real shape of the problem:** each delegate `i` has already produced a cardinal cost `cost_i(o)` for every surviving option `o` (a `ValuationProfile`, Decision 4 below) — costs are *within-person* comparable (spec: "arbitrary-but-consistent unit... across one household's whole matrix," which Phase 8 established means consistent *for that one person's own matrix*, never claimed comparable *across* people). Any mechanism requiring inter-personal cardinal comparability — a raw utilitarian sum, or literal Maximum Nash Welfare's product-of-utilities (which additionally requires non-negative, zero-anchored utilities, and is a real, well-established result *for goods allocation*, Caragiannis et al. 2019 — genuinely the right call had this been a divisible-goods problem, but not this one) — would be asserting a comparability this system has never actually established between two different people's cost matrices. Making that assertion silently would be exactly the kind of unearned precision this project has refused everywhere else (ADR-014's own chores/goods distinction; Phase 9/11's thin-history honesty).

**Decision: minimax regret over each delegate's own within-person-normalized cost (Savage, 1951 — a real, standard decision-theory criterion, not invented for this project).** For each surviving option `o` and delegate `i`: `regret_i(o) = cost_i(o) - min(cost_i(o') for o' in surviving options)` — how much worse `o` is for person `i` than *that same person's own* best surviving option. This never compares raw cost units across people; it only ever compares a person's cost against their own other options. `council_arbiter.resolve()` selects the option minimizing `max_i(regret_i(o))` (minimax regret); ties are broken by **leximin refinement** (compare the next-highest regret, then the next, a standard, well-founded refinement of egalitarian/minimax social choice rules — not an arbitrary tiebreak); a final, explicit, documented arbitrary tiebreak (lexical `branch_id` order) only if a genuine leximin tie survives, matching this project's own precedent of naming an arbitrary-but-deterministic final tiebreak outright rather than leaving one implicit (Phase 11's `RankedOutcome` tie-breaking).

**Hard constraints eliminate before scoring, never enter the cost matrix.** A43 Care's `HARD`-severity constraints (and any other specialist's `HARD` constraint) prune the surviving-branch set *before* Phase 4 interest scoring runs at all — an eliminated option is never assigned a cost by any delegate, matching Gate 12's explicit "hard constraint ELIMINATES options, does not score them down."

**The trade-off statement, computed not narrated:** for the winning option, `council_arbiter.resolve()` reports `most_costly_to` (the delegate with the highest regret for the winner — who "loses" most) and `most_favorable_to` (lowest regret — at or near their own top pick), with every number traceable to a real `ValuationProfile.costs` entry. Every delegate with `regret_i(winner) > 0` is a real concession — A49 Recorder writes a `CONCEDED_BY` edge (`Decision` → that `Person`) for each, reusing `concession_ledger`'s existing read path unchanged; Phase 8's own renegotiation flow already proved this exact write/read round-trip for a non-Council `Decision`.

**Alternatives considered and rejected**, for the record: (1) Maximum Nash Welfare — rejected above, real interpersonal non-negative utility comparability this system doesn't have. (2) Utilitarian sum — same comparability problem, and additionally scale-dominated by whichever delegate's matrix happens to use larger numbers. (3) A learned/LLM-scored resolution — directly forbidden by spec's own design rule 3 ("resolution is computed by the deterministic arbiter, not decided by a synthesizer agent").

## Decision 4 — Council's own `ValuationProfile`s are decision-scoped, never a reuse of Fair Allocator chore-cost values

A47 Member Delegate writes a **new** `ValuationProfile` per decision, `costs` keyed by `str(branch_id)` (this decision's surviving options), never reading or reusing a person's existing chore-era `ValuationProfile` — a person's cost for "doing the dishes" has no relationship to their cost for "which car to buy," and treating the two as interchangeable would be a real correctness bug dressed up as reuse. What genuinely is reused: the *type itself* (same shape: `person_id`, sparse `costs` dict, `elicitation_method`), the sparse-by-omission discipline (A47 is forbidden from inventing a preference the elicitation doesn't support — never fabricates a cost, exactly A18's own established rule), and the "visible and correctable by the person it represents" UI convention already established for A18/A19's costs (E4).

## Decision 5 — A49 Recorder needs no new persistence mechanism

Checked directly: `FirestoreGraphWriter.write_node`/`write_edge` are already fully generic (confirmed Phase 11), and `FirestoreDecisionRepository`/`GraphReader.concession_ledger`/`decisions_touching` already read any `Decision`/`Branch`/`CouncilPosition` generically. A49 is a **deterministic** module (no `AgentId` on the Pro-tier allowlist, no model call at all — same status as A15 Obligation Writer) that calls the existing generic writer directly: one `CouncilPosition` per specialist/delegate/adversary output (never summarizing them — spec's design rule 2, enforced by A49 holding no aggregation logic, only a 1:1 wrap-and-write), plus the arbiter's `CONCEDED_BY` edges. No new repository file needed this phase.

## Decision 6 — R4/no-auto-execute is structural, not procedural

The Council writes only `Decision`/`Branch`/`CouncilPosition` and `CONCEDED_BY` edges — all four are informational/historical node types with no execution semantics (same status Phase 11 established for the Simulator). **No module under `backend/app/agents/council/` imports `app.arbitration`, `app.tools.registry`'s gated-tier machinery, or any T4/T5/T6 tool** — checked structurally by the same AST-based boundary test used for Phase 7/10/11's agent packages. `Decision.status` is set to `BRIEFED` by A41's convening step and never advanced to `RESOLVED` by any Council agent — `RESOLVED` (with a real `resolution_summary`) is set only when a human decision is later recorded, exactly Phase 8's own precedent (`renegotiation_trigger_agent.py` sets `RESOLVED` only once, for its own already-human-confirmed concession — a materially different case from an unresolved R4 brief).

## Decision 7 — Adversary and Arbiter run against the same resolved option, no feedback loop

Spec's Phase 5 (Adversary) is described before Phase 6 (Arbiter) in prose, but functionally the Adversary's target — "the leading option" — is the arbiter's own deterministic pick; there is no earlier, separate "leading option" concept anywhere else in the protocol, and spec's own design rule 2 forbids any agent's LLM output from feeding back into the deterministic arbiter's math. **Implementation order: `council_arbiter.resolve()` runs first (pure function, only needs published interest scores + surviving branches); A48 Adversary then attacks that same winning option**, citing real household `OUTCOME` history via `GraphReader.history`/`outcome_variance` (reusing Phase 11's own real-citation discipline, never a generic risk template) — both land in Phase 7's brief together. A48 holds no path back into the arbiter's computation.

## Post-implementation correction (2026-08-29)

Decision 6 originally stated "`Decision.status` is set to `BRIEFED` by A41's convening step." Checked directly against the real, already-built `convener_agent.py`: it writes `status=DecisionStatus.OPEN`, correctly — nothing is ready to brief at convening time, before any specialist has even reported. Nothing in the pipeline advances it to `BRIEFED` either, because no real consumer of that distinction exists yet (no UI or downstream process currently reads `BRIEFED` specifically instead of `OPEN`). The actually-load-bearing guarantee — the only one Gate 12 tests — is that `RESOLVED` is never reached by any Council code path, proven by test (`test_council_structural_invariants.py`). Leaving `Decision.status` at `OPEN` throughout an automated Council run is the honest current state, not a bug: **this sentence in Decision 6 is corrected to read "`Decision.status` stays `OPEN` throughout an automated run and is never advanced to `RESOLVED` by any Council code path; a future `BRIEFED` transition belongs to whatever mechanism actually delivers a finished brief to the household, which does not exist yet."**

## Consequences

`contracts/graph_types.py`: one new `ConstraintKind.EDUCATION` member. No new node or edge types. E1: `backend/app/graph/scoped_reader.py` (`ScopedGraphReader`, `GraphSubgraphScope`, `OutOfScopeGraphAccess`, the five scope constants), `backend/app/solvers/council_arbiter.py` (pure `resolve()`), verification (not new code) that `CouncilPosition`/`CONCEDED_BY` persistence and reads already work generically. E2 (lead): `backend/app/agents/council/` — A41 Convener, A42-A46 specialists (each constructed with exactly its own `ScopedGraphReader`, no other), A47 Member Delegate, A48 Adversary, A49 Recorder (deterministic). E4: the Council view (positions with evidence, the explicit trade-off statement, the permanent record) and the historical decision browser — the latter needs no new backend endpoint at all, since `decisions_touching`/`concession_ledger`/`branches_for`/`positions_for` already exist and are already exposed via the graph API's existing node-inspector/justification machinery (Phase 6).
