## The complete graph model you are building (spec §5.2, §5.3 — memorise this, don't just skim)

**17 node types**, each with its own field shape (full detail is in `contracts/graph_types.py`, which you build to exactly — this is the conceptual map):

PERSON (identity/aliases/role/availability/capability flags/contact channels/language profile/voiceprint) · CONSTRAINT (dietary/medical/schedule/financial/religious/legal/custody/mobility; hard vs soft; validity window; structured + original text) · OBLIGATION (title/type/due/must-start-by/effort/status; **derivation: stated | implied is the single most important field on this node**) · LEDGER_EVENT (debit/credit/due/mandate created/cancelled/price change/refund/salary/advance) · RECURRING_COMMITMENT (label/counterparty/amount/cadence/price history/last-used/status) · VENDOR (category/contacts/job history/reliability/latency) · PROVIDER (ratings/distance/availability/price band/specialisations/interaction history) · DECISION (question/trigger/status/resolution/rationale — **permanent, never pruned**) · BRANCH (one option within a Decision, projected impacts, grounding refs, critiques) · COUNCIL_POSITION (one agent's stance, reasoning, evidence — **what makes the council auditable rather than mystical**) · OUTCOME (predicted vs actual, variance, attribution — the calibration substrate) · SOURCE_DOCUMENT (raw payload ref, channel, extraction record — every derived node points back here) · ACTION_RECORD (what the system did, when, under whose approval) · APPROVAL_REQUEST (proposed action, evidence bundle, risk tier, confidence, status) · PURCHASE_ITEM (description, normalized category, quantity, unit price, line total — **the finest-grained evidence node in the system**) · PATTERN (a mined regularity, e.g. "Dad's appointments always slip when scheduled on Mondays") · ATTENDANCE_RECORD (one staff member, one month: rollup counts, real per-day marks, advance annotations kept cross-reference-only — added Phase 7, ADR-013, DEBT-004's repayment).

**34 edge types** (`EdgeType` enum member count — history: spec §5.3's table has 29 rows but `supports`/`opposes` is one row for two distinct members, so the true original count was 30; ADR-005 (Phase 1) removed the unresolvable `argued_by`, bringing it to 29; ADR-009 (Phase 3) added `covers` (OBLIGATION→PURCHASE_ITEM, a real spec §5.4.2 relationship the original table never gave its own edge type), back to 30; ADR-012 (Phase 5) added `acts_on` (ACTION_RECORD→{OBLIGATION|LEDGER_EVENT|VENDOR|PROVIDER|RECURRING_COMMITMENT}), `authorizes` (APPROVAL_REQUEST→ACTION_RECORD), and `approved_by` (APPROVAL_REQUEST→PERSON) — DEBT-002's repayment, the first edges ever connecting these two node types — to 33; ADR-013 (Phase 7) added `attendance_of` (ATTENDANCE_RECORD→PERSON) — DEBT-004's repayment — to 34), all typed and directional — the full table lives in the `gharos-graph-model` skill; the ones you must never get wrong on layout because they're the verification-loop edges (spec §5.5) are: `line_item_of` (PURCHASE_ITEM→LEDGER_EVENT), `discharges` (PURCHASE_ITEM|LEDGER_EVENT→OBLIGATION), `verifies`/`contradicts` (PURCHASE_ITEM→CONSTRAINT), `absent_from` (CONSTRAINT→SOURCE_DOCUMENT[] — expected evidence that never arrived, a first-class signal, not a null result), `substitutes` (PURCHASE_ITEM→PURCHASE_ITEM), `evidences_effort` (PURCHASE_ITEM|LEDGER_EVENT→PERSON — a primary Fair Allocator input, not a side effect).

## Provenance enforcement — your single most important defence (spec §5.6)

Every node and edge carries: `derivation` (`extracted` | `inferred` | `ambiguous`), `source_ref` (pointer to SOURCE_DOCUMENT + region), `confidence` (numeric), `deriving_agent`, `created_at`, `superseded_at`. **A write missing any required field must be REJECTED by the repository at write time** — not logged, not warned about, rejected. This is what turns "the agent decided" into "here is the path it walked," and it is what lets a human check rather than trust. Prove this is unbypassable with a `hypothesis` fuzz test, not a handful of example-based unit tests — Gate 1 requires this specifically.

Versioning: writes create versions; `superseded_at` is set on the old version, never overwritten in place, and the old version is never deleted (except where PHASES.md Phase 14's Graph Maintainer explicitly permits pruning of non-protected types — DECISION, OUTCOME, provenance records, and hard-constraint nodes are **never** pruned, full stop).

## The 14 traversal operations you must implement (spec §5.7) — every subsystem depends on these existing and being correct

`neighbours(node, edge_type)` (obligations owned by Priya) · `path(a, b)` (why does this email affect Tuesday's lunch — the Path Explainer's core capability) · `blast_radius(node, depth)` (what breaks if we relocate in June — Simulator, Council) · `conflicts(scope)` (all unresolved collisions this week — Conflict Radar) · `load(person, window)` (Priya's obligation load this month — Fair Allocator) · `series(commitment)` (all debits in this recurring series — Ledger) · `history(entity)` (all outcomes for school-run obligations — Calibration) · `decisions_touching(entity)` (every past decision involving the car — Council) · `concession_ledger(person)` (who has conceded most, historically — Council) · `unexplained(scope)` (nodes lacking provenance — must be empty, an integrity check not a normal query) · `unverified(scope)` (graph claims with no real-world evidence behind them) · `expected_but_absent(constraint)` (constraints the receipts never confirm — silent non-compliance, feeds the Pattern Miner) · `spend_by_category(window)` (real spend from line items, not estimates) · `effort_evidence(person, window)` (who actually did the runs, from receipts and transactions).

## Firestore layout — follow ADR-001 unless you have a reason to write a new ADR

One top-level collection per node type (e.g. `persons`, `obligations`, `constraints`...), document ID = NodeId, `provenance` embedded as a map matching `contracts.graph_types.Provenance` field-for-field. One flat top-level `edges` collection (not subcollections), with composite indexes on `(from_id, edge_type)` and `(to_id, edge_type)` for bidirectional traversal. `blast_radius`/`path` are repository-layer BFS/DFS over `edges`, depth-bounded. If Firestore traversal performance becomes a bottleneck at demo graph size (spec §27.2 open question #8), that is a new ADR, not a silent workaround.

## Architecture discipline (PHASES.md §2.2) specific to your domain

- **Hexagonal / ports-and-adapters.** Your domain logic imports no framework code where avoidable — Firestore specifics stay behind the repository interface; `backend/app/agents/` (E2) never imports `google.cloud.firestore` directly, only your repository protocols.
- **Repository pattern**, always — every one of the protocols in `contracts/repositories.py` (`GraphReader`, `GraphWriter`, `PersonRepository`, `ObligationRepository`, `DecisionRepository`, `PatternRepository`, `AuditLog`, `IdempotencyStore`, `GraphIntegrityChecker`) gets a concrete Firestore-backed implementation from you.
- **Immutability by default.** Graph writes create versions; they do not mutate in place — this is not a style preference, it is what makes the audit trail honest.
- **Result types** for expected failure paths per ADR-002; typed exceptions from `contracts.errors` (`ProvenanceMissing`, `IdempotencyConflict`, etc.) for conditions a specific caller up the stack is expected to catch.

## Audit log and idempotency — the mechanisms behind two of the eight invariants

- **Audit before execute (invariant #2).** Your `write_before_execute` helper in `backend/app/audit/` must make this structural: an `Action` (contracts.actions.Action) cannot reach `execute()` with a `None` `audit_ref` — this is not "please remember to call audit first," it is a type-level or runtime-enforced precondition you build.
- **Idempotency (spec §19.1).** Keys generated from `(entity_id, action_type, cycle)`. Payments are strictest: one debit per due-ID per cycle, enforced at the *tool* level (E3 calls into your `IdempotencyStore`), not the agent level. Demonstrate resilience: kill a run mid-flight, restart, show no duplicate effect — this needs to actually work, not just look plausible in a happy-path test.

## Deterministic solvers (spec §16.2) — code tools, never LLMs, arrive in later phases but design for them now

- **Fairness solver** (Phase 8) — Maximum Nash Welfare / competitive-equilibrium machinery for the Fair Allocator. State exactly which guarantee is delivered (EF1+PO is proven for goods; chores/bads are subtler — see `docs/FAIRNESS_GUARANTEE.md`, which you and the CTO co-own the accuracy of).
- **Council mechanism arbiter** (Phase 12) — computes decision resolution from published COUNCIL_POSITIONs and constraints. Deterministic by design; this is what prevents the Council from degenerating into LLM consensus-generation (spec §12.2). Reuses fair-division machinery conceptually but applied to a decision, not a chore list.
- **Salary calculator** (Phase 7) — days − absences − advances, pure arithmetic, no LLM judgment in the computation itself (attendance *interpretation* is E2's Pro-tier agent A34; the arithmetic delegated to your tool is deterministic).
- **Calibration/variance calculator** (Phase 11) — this household's own OUTCOME variance, feeding the Simulator's Calibration Agent. Thin history → the calling agent must say so, never fabricate false precision; your tool should make "insufficient sample size" a distinguishable, checkable output, not a silent guess.
- **Deterministic conflict detector** (Phase 4) — runs *before* the reasoning pass in the Consequence Engine, catching mechanical conflicts (double-booking, resource contention) cheaply before Pro-tier reasoning is spent on them.
- **Idempotency key generator**, **Graph integrity checker** (orphans, missing provenance, dangling edges — must be clean on seeded demo data at every gate from Phase 1 onward).
