## The design system — own it once in Phase 0, never re-invent per screen (PHASES.md §3.2)

**Direction:** GharOS reads as a well-kept household *ledger and archive that happens to think* — not a productivity SaaS dashboard. Deep lapis and antique brass on warm parchment; the same palette inverted to ink and candlelight in dark mode. Rich and royal, but archival rather than luxurious. Every screen should feel like it belongs in the same bound ledger, not like a different app per subsystem.

**Required CSS custom-property tokens, both themes, no exceptions:** `--surface-base`, `--surface-raised`, `--surface-overlay` · `--ink-primary`, `--ink-secondary`, `--ink-muted` · `--royal-primary`, `--royal-deep`, `--royal-soft` · `--accent-brass`, `--accent-brass-muted` · `--state-success`, `--state-warning`, `--state-danger`, `--state-info` · **derivation colours, load-bearing not decorative:** `--derivation-extracted`, `--derivation-inferred`, `--derivation-ambiguous` · `--edge-conflict` (the red that matters) · spacing, radius, elevation, motion scales.

**Rules:** both themes are first-class; dark is not an inverted afterthought. WCAG AA minimum — actually measure contrast ratios, don't eyeball them. No raw hex anywhere in a component — tokens only, enforced by you in code review of your own work. Motion is purposeful: the graph growing is the one place animation carries real meaning; gratuitous motion elsewhere undercuts that one moment. Typography: one display face with character for headings, one highly legible face for data and body.

Build `/tokens` rendering every token in both themes — this is the review surface for the whole system and a Gate 0 item; organise by category, not as an undifferentiated dump.

## The graph visualisation — your single most persuasive demo artifact (spec §5.8, PHASES.md Phase 6)

A live force-directed rendering (D3, or Cytoscape.js if performance demands — record an ADR either way, your call to make and defend): nodes coloured by type, **edges styled by derivation tag** — solid = extracted, dashed = inferred, dotted = ambiguous — conflict edges rendered in `--edge-conflict`.

**Demo behaviour, non-negotiable:** when a source document arrives, the graph must visibly *grow* — new nodes appear, edges connect them to existing household structure, a conflict edge lights up red. This is the "holy shit" moment: the graph assembling itself out of mess, in real time. **If it looks hand-seeded or replayed instead of built live, a judge will sense it and the whole provenance pitch collapses with it** — this is the highest-stakes visual claim in the project and you own making it real.

Also build: a node inspector → provenance panel with the source region highlighted; a **path explainer** that turns a selected conclusion into a walkable, legible chain back to its source (this is literally what A9 Path Explainer's output looks like rendered); filters by type/person/time-window/derivation; performance validated at 500+ node demo scale.

## Per-subsystem UI requirements — what each surface must make visibly true (pulled from the spec sections that define each subsystem's demo beat)

- **Approval Gate (spec §18.2, referenced everywhere money or calls are involved):** must always be visibly shown before any money moves or any call is placed. Never let a demo path show an agent spending or calling without a visible confirm step. Render the full evidence bundle: proposed action, reasoning, evidence consulted, confidence, consequence-if-wrong. Expiry escalates visibly — never silently auto-approves.
- **Fair Allocator / cost matrix (spec §8.3, §8.7):** the cost matrix must be **visible and confirmable, never hidden** — this is explicitly what distinguishes GharOS's fairness claim from a black-box allocation. Per-person explanations must reference that person's own stated valuations, not a generic justification. Support live re-allocation on a triggered life event (e.g. "I just started night shifts") with a visible before/after.
- **Household Ledger (spec §10.7):** a running recovered-money counter ("found ₹X/year of leakage — three claims drafted, awaiting approval"), a dispute UI that presents both conflicting figures without picking a winner, and a payroll review that shows the handwritten register image *beside* the computed salary figure — never just the number alone.
- **Household Council (spec §12.2, §12.8):** positions rendered with their evidence and an explicit trade-off statement — **never a synthesized consensus paragraph**. The historical decision browser ("why did we buy this car?") must surface the actual DECISION node, every COUNCIL_POSITION, the trade-off, and who conceded — this is institutional memory as a UI feature, not just a data model. Never use the word "debate" anywhere in UI copy, labels, or tooltips.
- **Household Simulator (spec §11.6, §11.4):** branch comparison with every claim traceable to graph data or a cited external source with a retrieval timestamp; a risk register per branch; an interrogation mode ("what if the budget were 15% higher?"); present trade-offs, never a verdict on an emotionally-loaded family decision.
- **Voice surfaces (spec §14.6, §14.12):** live transcript with **per-span language tags** (not per-utterance — a single sentence can carry two or three languages), confirmation prompts that visibly enforce the read-back discipline (amounts digit-grouped and repeated, names shown with relationship, explicit affirmative required), and session state. Never let a UI imply an action was approved by silence or ambiguity — the absence of a clear "yes" must render as *not approved*, visibly.
- **Escalation surface (spec §7.7, §18.1):** when the system declines to guess (e.g. an ambiguous child's name on a form with a hard constraint attached), the UI must show the raw evidence (the image, the ambiguity) and the system's own reasoning for not resolving it — "the agent knowing when not to act" is itself a UI moment, not just a backend log line.

## The demo script — what you're ultimately building toward (spec §24, full timeline)

0:00-0:20 problem framing · 0:20-0:40 trigger (a chaotic email lands, agent wakes with no user present) · **0:40-1:40 autonomous execution + the graph assembling itself live** (extraction visible, six obligations with five implied, provenance edges, conflict edge lighting up red, temporal collision caught, Fair Allocator's one-line assignment reason, Firestore writes live) · **1:40-2:20 the outbound call** (two clarifying questions, ranked shortlist with reasons, approval gate shown, live call audible, adapts when the slot's gone, verified booking, calendar entry, graph updated) · 2:20-2:40 voice/multilingual (20 seconds, per-span language tagging visible, do not let this become the centrepiece) · 2:40-3:05 the Council (specialists reporting from different subgraphs, Care's hard constraint eliminating options not scoring them down, delegates in genuine conflict, Adversary landing a hit, deterministic arbiter's explicit trade-off) · 3:05-3:25 the live exception (ambiguous entity → escalates, doesn't guess) · 3:25-3:40 outcome metrics · 3:40-4:00 architecture + Google Cloud proof, OS framing named last. Every surface you build should make one of these beats land cleanly on camera — if a screen doesn't serve one of these beats or the judge's post-demo exploration, question whether it needs to exist yet.

## Accessibility (spec §14.11) — not an afterthought given who the product is for

Elderly members with limited literacy or poor eyesight, domestic staff who may not read English, hands-free operation for anyone mid-task, adjustable pacing and patient re-prompting without penalty, a voice-only mode for people who will never use the visual surface at all. Build with this population in mind from the first component, not retrofitted later.
