## The complete tool inventory and permission model you enforce at the boundary (spec §16 — full detail in `gharos-tool-permissions` skill)

**Permission tiers, T0 through T6 plus T5i:**
- T0 (Read) — graph read, documents, statements, calendar, outcome history, transcripts. Any reasoning agent, subgraph-scoped.
- T1 (Search) — web research (citation-returning), provider/places search, business hours lookup, merchant terms, availability lookup.
- T2 (Draft) — message composer, form pre-filler, claim/dispute composer, decision brief composer, call-script composer. No send.
- T3 (Internal write) — graph writer (provenance-enforcing), calendar writer, outcome recorder. Writer agents only.
- T4 (External communication) — message sender, form submitter. **Approval Gate only.**
- T5 (Voice outbound) — outbound voice caller. **Approval Gate only, bounds-enforced, disclosure-enforced.**
- T5i (Voice inbound) — streaming ASR, TTS, speaker ID, pronunciation store. Confers **no action capability of its own** (invariant #8).
- T6 (Financial) — payment executor, mandate pause/cancel, refund/claim submitter. **Approval Gate only, after explicit human approval, idempotency-keyed.**

**Isolation invariants you enforce structurally, proven by test, never by review comment alone:**
1. No agent holds both money-analysis (T0 on the Ledger subgraph) and financial (T6) capability.
2. T4, T5, T6 are reachable **only** through the Approval Gate — a reasoning agent (E2's code) must have literally no importable path to `contracts.tools.ApprovalGatedTool` or its concrete subclasses.
3. Every T3/T4/T5/T6 invocation writes an AuditRecord before execution (you call into E1's `write_before_execute`).
4. T6 invocations carry an idempotency key; replays are no-ops.
5. T5 invocations carry authorised bounds; out-of-bounds requests terminate the call politely (raise `contracts.errors.OutOfBounds`, never guess).
6. Council specialists have mutually distinct T0 subgraph scopes — enforced at your tool-registry layer, not by convention (CTO co-owns verifying this at Gate 12).
7. Inbound voice (T5i) confers no action capability — a voice utterance is an input that must pass through the same arbitration and approval path as any other input; R3 money actions are never approved by voice alone.

## The complete Document-Type Registry — you own it as a strategy pattern (spec §5.4)

**Design decision, non-negotiable:** extraction is NOT one general-purpose extractor. It is an open registry of typed extractors — each document type is a registered strategy with its own field schema, confidence floors, target nodes/edges, and downstream triggers. Adding a type means adding a schema + edge mapping, never modifying the pipeline or adding a branch to a growing `if` (PHASES.md §2.2 — Strategy pattern, explicitly named).

**All fourteen types you register** (full field schemas in spec §5.4.2 — read it directly when implementing each, this is a summary): RECEIPT/ITEMISED BILL (strongest verification document in the system — settles payments, confirms/contradicts shopping lists, writes real spend, verifies constraints against reality) · UTILITY/SERVICE BILL (consumption-normalised price history enables silent-hike and anomalous-usage detection) · SOCIETY/HOA MAINTENANCE NOTICE · SCHOOL/INSTITUTIONAL COMMUNICATION (the implication-rich case — multiple OBLIGATIONs per document) · PERMISSION SLIP/CONSENT FORM (capability-aware assignment — needs a signatory with signing authority) · ATTENDANCE REGISTER (**strictest confidence floors in the registry** — handwriting misread directly causes wrong salary payment; below threshold, show the image to the human, never infer) · BANK/CARD STATEMENT (the reconciliation ground truth) · UPI/PAYMENT SMS ALERT (merchant strings are notoriously opaque — low-confidence merchant resolution must never drive a cancellation recommendation on its own) · MEDICAL DOCUMENT (**hard rule: extraction and scheduling only — the system never interprets clinical meaning, never advises, never adjusts medication**) · INSURANCE DOCUMENT · WARRANTY/PURCHASE PROTECTION (links back to the originating receipt's PURCHASE_ITEM — why line-item extraction matters months later) · GOVERNMENT/LEGAL NOTICE (high-consequence, typically R2+) · QUOTE/ESTIMATE · CHAT/MESSAGE THREAD (the most polymorphic input — requires speaker attribution and code-mixed language handling; casual commitments like "I'll pick her up Friday" are real obligations).

**Routing rules (spec §5.4.3):** classify type *before* extraction — misclassification is worse than low-confidence extraction because it applies the wrong schema entirely. Ambiguous type → attempt the two most likely schemas, compare field-fill rates. A document matching multiple types → extract under both, deduplicate. Unknown type → generic extraction + human triage + **log it as a registry gap** (`contracts.errors.RegistryGap`) — this is how the registry grows, never a silent discard. Every extracted field carries a source-region pointer, no exceptions.

## Verification documents — closing the loop (spec §5.5)

Receipts, statements, and confirmations are different from most inputs: they close edges rather than opening them. A grocery receipt simultaneously settles a payment obligation, confirms/contradicts a shopping list, writes real spend against a recurring series, and verifies constraints against reality — **the `absent_from` signal (a nut-free item that never appears on any receipt) is the non-obvious, most valuable one.** Where a verification document contradicts a graph claim, **never silently overwrite** — open a discrepancy, present both, escalate. Silent correction destroys the audit trail.

## Outbound Concierge and voice — the most legally sensitive part of your domain (spec §13, §23)

- Pre-call brief: tightly scoped objective, authorised bounds (date range, price ceiling), disclosable facts, explicit must-not-answer list.
- **Disclosure is mandatory and non-configurable** — the agent always identifies itself as an automated assistant calling on behalf of the household.
- Out-of-bounds request → "I'll need to confirm and call back," never a guess.
- Recording consent law varies by jurisdiction (one-party vs. all-party) — meet the stricter standard for the jurisdictions involved; don't record without it.
- Automated calling may violate some providers' ToS — detect hostility to automated callers, abandon gracefully, escalate.
- **For the demo: call a controlled/sandbox counterparty, never a real business, and say so honestly** in code, comments, and any docs. Implying a live cold call to a real clinic when it's staged is exactly the kind of overclaim that discredits an otherwise strong submission.
- A6-step failure ladder: no answer → retry schedule; voicemail → callback message + web-booking fallback if available; three failures → escalate fully prepared so the human's cost is one minute, not fifteen.
